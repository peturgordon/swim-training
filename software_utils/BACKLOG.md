# Backlog (software_utils)

Ideas and prototypes for the swim-data tooling raised along the way but not yet built into a real module — distinct from the root [`BACKLOG.md`](../BACKLOG.md), which is about training-methodology/scheduling ideas, not code.

## Building the new visualization layer on `swim_data.py`

The three old tools (now in [`legacy/`](legacy/): `explore_pool_swim_json.py`, `swim_explorer.py`, `swim_primitives.py`) all predate the object model and have been set aside as the basis for new work — they still run and still produce their existing output, but nothing new gets built on them. All new visualization is meant to sit on top of `swim_data.py`'s objects (lap↔segment join, segment table with distance, segment-gap HR) plus the raw HR timeseries and the recovery-curve pipeline (`segment_gap_recovery_curves`/`aggregate_recovery_curves`) — starting fresh, not extending or porting logic from the legacy tools. First concrete piece: a plot of `aggregate_recovery_curves`' output as a mean line with a shaded band (min/max or ±2 SD, seaborn-`lineplot`-`errorbar`-style) — the recovery-curve pipeline itself is done (in `swim_data.py`), but nothing plots it yet.

## True lap duration bridging as a fourth object

`add_true_duration()` (still living in [`legacy/explore_pool_swim_json.py`](legacy/explore_pool_swim_json.py), never moved to `swim_data.py`) recovers the turn-time Apple's raw `elapsedDuration` excludes, by bridging each lap's true end to the next lap's start (or the segment's own end, for the last lap in a segment) — it depends on Object 1 (`tag_lap_segments`) already existing, which is exactly why it was proposed as the natural next step right after the lap↔segment join was verified solid. Got shelved when the conversation pivoted to reorganizing into `swim_data.py` instead. Still worth doing, and now has a natural home once it's ported over.

## Horizontal zoom + scrollbar for an interactive pace/HR viewer

Raised against [`legacy/swim_explorer.py`](legacy/swim_explorer.py), then tabled pending a design decision that was never made: real elapsed time is highly irregular (turn gaps of ~5-16s vs. rest gaps up to 200s+ in one session), so a naive linear zoom/scrollbar over true elapsed time makes rest periods eat disproportionate screen space when zoomed in on a tight set. Three options were on the table — real elapsed time as-is (simplest, most faithful), visually compressing large gaps (more complex, distorts true timing), or just adding standard pan/zoom controls now and revisiting gap compression only if it's still annoying in practice. Since `swim_explorer.py` is now archived rather than being extended, this decision applies to whatever new interactive viewer eventually replaces it, not to the old file itself. Largely superseded now that `swim_tables.py`'s graphs all carry a `NavigationToolbar2QT` (pan/zoom-rectangle/home), but the gap-compression question itself was never actually decided either way.

## Manual correction of lap↔segment assignment

`tag_lap_segments` (Object 1) assigns each lap's `seg_idx` via an automatic containment join (`lap.start >= seg.start and lap.end <= seg.end`) — its own docstring already flags that it doesn't guard against overlapping segments, and there's currently no way to override the result if the automatic join gets a lap wrong (e.g. a watch quirk around a segment boundary). Would need a GUI-side correction mechanism (most naturally: make the Laps table's "Segment" column editable, or a dedicated small dialog) plus a persistence design decision that isn't solved yet — corrections need to survive reloading the same export, so they probably want a sidecar file next to the archive (same shape as `hr_labeler.py`'s `_segments.csv`/`_annotated.csv` pattern, per [`WORKFLOW.md`](../WORKFLOW.md)) rather than living only in the live Qt widget state. `tag_lap_segments` itself would need to accept and apply that override on top of its automatic join, not just in the display layer, so every consumer (Segments table, distance totals, recovery-gap pipeline) sees the corrected assignment consistently.

## Import a practice's plan into the visualizer, with a lookup table from practice → recording

Right now `swim_tables.py` only knows the raw Apple Watch export — laps, segments, heart rate — with no notion of which block of the *planned* session (from [`practices/*.md`](../practices/) in the swim-training repo) each lap/segment actually corresponds to (e.g. "this was Warmup," "this was main-set rep 3"). The idea: import a practice file's plan and map it onto the recorded data, so the visualizer can label/annotate segments with the intended set name instead of just a segment index. This requires a workflow change upstream of the visualizer, not just a new feature in `swim_tables.py`: whenever a training programme/practice is generated going forward, it would need to also emit a machine-readable lookup table (e.g. a small YAML/JSON sidecar mapping block name → expected lap range, distance, or rep count) that the visualizer can read and join against the actual recorded laps/segments. Open questions: where that lookup table lives (alongside the practice `.md`, or alongside the archive), how it tolerates a session that didn't go exactly as planned (extra/missing laps, a skipped set), and whether the mapping is by lap-count/order or by some more robust anchor.

## Filter recovery-curve gaps by pre-gap peak heart rate, not just duration

`segment_gap_recovery_curves` currently filters candidate rest gaps only by `min_duration_s` (and optionally `max_peak_offset_s`) — nothing filters on how high heart rate actually was going into the gap. A rest gap that starts from an already-low HR (e.g. a pause during warmup) isn't a real "recovery from effort" curve, and averaging it into `aggregate_recovery_curves`' summary dilutes the signal for genuine post-effort recovery. Idea: add a `min_peak_hr` (or similar) parameter to `segment_gap_recovery_curves` so only gaps whose peak HR (already computed internally to find each gap's own reference point) exceeds a threshold get included — letting the Recovery tab ignore rests that were never really "recovering" from anything hard to begin with.

## `swim_data.py` edge-case bugs found in code review (not yet fixed — low priority)

None of these have been hit by real session data; all are unguarded edge cases found by reading the code, not observed failures. Deliberately left unfixed for now per explicit instruction (2026-09-25) — filed here so they aren't lost, not because they're urgent.

- `hr_stats`: assumes `heartRateAverage`/`heartRateMinimum`/`heartRateMaximum` are dicts whenever the key is present. If a JSON export ever has e.g. `"heartRateAverage": null` (key present, value explicitly null) rather than the key being absent, `.get("qty")` raises `AttributeError: 'NoneType' object has no attribute 'get'`.
- `intervals_to_df` / `heart_rate_df`: an empty `laps`/`segments`/`heartRateData` list (e.g. a workout with zero recorded laps) produces a DataFrame with no columns; the next line (`.sort_values("index")` / `df["date"]`) then raises `KeyError`. `swim_tables.py`'s `SwimTablesWindow.load` catches this via its broad `except Exception` and shows a `QMessageBox`, but the resulting error text ("'index'" / "'date'") would be meaningless to whoever sees it.
- `segment_gap_recovery_curves`: auto step-size detection (`hr["date"].diff()...mode().iloc[0]`) raises `IndexError` if `hr` has fewer than 2 samples. `gap["hr_avg"].idxmax()` would also raise if a gap's `hr_avg` column were ever all-NaN (very unlikely with real Watch data, but unguarded).
- `segment_gap_heart_rate`: no check that segments are non-overlapping/chronological after sorting; a violation degrades gracefully to a silently-empty gap DataFrame (caught downstream by `segment_gap_recovery_curves`'s `len(gap) < 2: continue` guard) rather than crashing, so not a functional bug today, just an unstated assumption worth documenting or asserting explicitly if it ever bites.
